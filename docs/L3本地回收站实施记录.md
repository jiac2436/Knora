# L3 本地回收站实施记录

日期：2026-10-01。承接已完成的备份、客户端恢复和可读导出，本轮实现本地资料回收站与用户确认后的永久清理。

## 用户流程与保留策略

本地删除资料时移入回收站，立即从资料列表、搜索、正文和历史证据读取入口隐藏；原件、图片、版本、补充和既有分析记录仍保留。设置新增“回收站”，支持刷新、分页、恢复与单条永久删除确认。

当前明确采用**不按天自动清理**策略。未添加自动期限或整站一键清空；用户可主动永久删除单条资料。后续引入清理周期时需要独立配置及明确产品告知，不以此实现承诺无限存储容量。

恢复前校验原件路径、文件大小和 SHA-256；缺失、损坏、路径穿越、根目录/父级/子路径链接均拒绝恢复，原回收站状态保留。列表的 `can_restore` 表示当前删除流程允许恢复，不等于已计算所有原件摘要；完整检查发生在点击恢复时。

恢复保留资料 ID、原件、历史版本、证据和补充，并重建关键词及语义索引任务。删除时取消尚未完成的文档/OCR/网页任务，恢复后这些任务转为失败、提示手动重试，不自动重新调用解析器。删除、恢复不会替换已保存原件。

永久删除确认后将资料标记为 `deleting`，提交 Worker 清理任务；此时不能恢复。客户端显示“已提交”，不提前声称已经清理完成。Worker 清除原件、图片、正文版本、证据、补充、经验、标签、项目关联和索引等，保留现有最小资料墓碑及操作记录。失败可再次提交，清理中的本地任务在 Worker 重启时续跑。**已有备份中的资料不会因此被清除**，确认框已说明。

## API 与并发

仅本地模式开放，非本地模式返回 404，保持原来的远端删除契约。

| 接口 | 行为 |
| --- | --- |
| `GET /v1/trash?limit=50&offset=0` | 当前 owner 的回收站列表及 `next_offset`；limit 为 1–100 |
| `POST /v1/trash/{source_id}/restore` | 恢复可用资料，返回 `id/status=restored` |
| `DELETE /v1/trash/{source_id}` | 提交永久清理，202 返回 `operation_id/status` |
| `GET /v1/operations/{operation_id}` | 沿用现有操作状态查询 |

恢复和清理都先条件更新 Source 行获取 SQLite 写锁，再读取任务状态并提交。恢复拒绝清理中、失败待清理或已清理状态；重复提交清理复用任务。恢复包会移除旧删除任务记录，所以回收站也支持“有 deleted_at、没有 DeletionJob”的完整资料；仍通过 Source 条件写锁保护恢复与清理竞争。

Worker 的初始领取、成功产物提交和异常状态提交都在本地模式下条件更新 Source，并检查对应任务的 pending/running 状态。这样，读取任务后发生删除/恢复的旧 Worker 不能继续领取，已经开始的旧提取也不能覆盖恢复后的正文或错误状态。永久清理仅领取已经确认 `deleting` 的本地源，避免未经确认的旧 pending 删除任务直接清理。

客户端用独立回收站代次以及地址/凭证检查忽略过时响应；与采集、浏览、备份和切库互斥，切库或断连时清空列表。请求失败保留原行；已经确认恢复或提交清理后，即使刷新失败也更新原行状态，避免继续展示错误的“可恢复”。

## 兼容性

无数据库 DDL 迁移和新依赖，不迁移旧数据。持久化语义增加 `DeletionJob.status=trashed/cancelled` 以及 `Source.processing_status=deleting`。本地删除现在返回 202/trashed，不再马上进入物理清理；已有调用者不能再把本地删除响应视作物理删除完成。

API、Worker 与 Mac 客户端随运行包统一更新。旧客户端没有回收站入口，降级会失去新流程的完整状态保护，不建议对已使用回收站的本地库降级。远端仍返回 pending 并按原流程清理；没有顺带改变其恢复机制。

## 当前边界

主要本地 L3 功能已落地，完整验收仍未结束。当前使用单 Worker 和本地 SQLite；图形确认框实机操作、多实例并发、大库、真实满盘/中断/断电、长期备份兼容以及发行签名仍待验收。文件清理和数据库提交无法组成跨文件系统原子事务；清理失败可能已有部分原件被删除，因此一旦提交永久清理就禁止恢复，并通过幂等任务重试完成，不能靠回滚把原件找回。
