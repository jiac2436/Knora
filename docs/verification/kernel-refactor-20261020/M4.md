# M4：正式本地采集接管与飞书加工迁移

状态：**工程验收完成，正式App未替换**。依据[总方案](../../design/客户端内置模型与共享内核实施方案-2026-10-20.md)的B2／M4，具体交接契约见[M4设计](../../design/M4-采集任务与旧队列交接.md)。不提前实施M5发布，也不把免费工程测试当作真实模型质量通过。

## 实现与责任边界

- `app/capture_contract.py`、`capture_handoff.py`、`capture_store.py`、`capture_queue.py`负责Owner采集契约、旧队列交接与私密持久队列。`services/worker/capture.py`负责已提交任务执行，接在删除任务之后；`files.py`、`images.py`抽出共享归档事务，原HTTP上传接口保持兼容。
- 正式本地客户端的`KernelCaptures.swift`只提交条目、保存接收回执和展示状态。领域／项目在提交时冻结；收到过时或跨库响应不更新界面；未改变的状态不重复发布或写盘。客户端仍负责草稿、文件选择、未提交暂存及CLI登录交互，未重写阅读器和页面切换缓存。
- `app/feishu_capture.py`统一处理飞书正文／XML同版本核对、图片清单、Markdown替换、下载与官方预览回退、总量和格式限制、OCR及逐张检查点。已有正文与部分上传图片从检查点续接，不重复抓取或建资料；OCR失败保留有效原图，存储失败保留任务，不默认为部分成功。
- `platform_support/external_macos.py`通过一次性原生`KnowledgePlatform`调用M3受限CLI和Apple Vision。辅助程序无监听端口，不保存知识规则或模型凭证；有界私有请求／响应、超时和父进程EOF回收只作用于本次拥有的进程。运行包构建器先编译签名辅助程序再生成清单，`build.sh`拒绝缺少辅助程序的旧运行包；客户端握手要求`capture_queue`能力。

## 持久化、恢复与兼容

1. schema仍为16，插件仍为1.0.5，无新表或依赖。正式知识继续进入原SQLite、assets、版本与幂等记录。设备执行日志位于`<data>/jobs/capture-queue-v1/`，不进入备份、同步或可读导出；恢复库不自动执行旧设备任务。
2. 先校验、复制当前库相对原件，原子发布接收回执；客户端持久保存回执后才删除旧副本及释放已交接正文。响应丢失、客户端落盘失败、接收失败均保留可恢复原件。拒绝越界、符号链接、摘要变化、所有者不符和同编号不同输入。
3. 保留原条目UUID字符串大小写作为SQL幂等键，执行目录名称规范化。已有SQL回执还必须核对冻结内容摘要；不能仅凭同Owner的编号确认成功。SQL提交后执行日志中断仍能找到同一资料，已保存图片按稳定ID／SHA跳过。
4. 自动交接只处理旧v1队列中已指定目标、属于当前Owner的条目；草稿和未提交条目留客户端。损坏记录、未知版本、原件缺失或损坏不改写原队列，逐项报告。队列损坏不阻断其他阅读、OCR与索引。
5. 采集`running`在重启时回到待接续状态，免费读取／归档按检查点继续；失败需要显式重试，不创建AI任务，也不改变付费任务未知结果不重放规则。终态移除只清设备暂存、保留防重放回执；失败图片结束pending状态。永久删除资料联动清除设备复制件，旧编号不能重新采集已删除资料。

**保留的过渡兼容入口**：明确选择外置开发API的客户端仍调用旧`sendCompatibilityCaptures`及Swift飞书方法。正式随包本地App走共享内核；本阶段没有删除这些历史方法，以免破坏既有开发入口。Windows/Linux只保留接口设计，未实现或验收其客户端和CLI／OCR适配。
