## 结论

项目已有客户端源码、测试、运行包构建工具及 DMG 产物，具备整理为公开项目的基础；目前不建议直接将整个工作区加入 Git 后公开。优先完成许可证、第三方声明、公开材料筛选、最新源码入库和干净环境构建说明。

上传源码、允许他人按开源许可证使用源码、向普通用户发布可安装版本，是三个不同的交付环节。Developer ID 签名、公证不属于上传源码的前置条件；当前未公证 DMG 应标注为测试发行物，不能声称已经完成跨设备正式发行验收。

## 第三方许可的具体问题

`apps/macos/Sources/MarkedLib.swift` 内嵌 Marked JavaScript，目前没有版本标记、版权声明和许可证文本。Marked 的上游许可证要求保留相应声明，应先确认本项目实际使用版本，再交付对应许可文本。

当前基础 App 的 Python 运行环境内能找到 38 份名称含 LICENSE、COPYING 或 NOTICE 的文件，说明部分上游许可已随包保留；不能据此认定全部依赖的分发义务都已满足。建议生成基础 App 与各扩展分别对应的依赖清单和第三方声明，重点覆盖：

- 内嵌 Marked、CPython 及随包 Python 依赖。
- PDFium / pypdfium2 及其随附依赖许可。
- OCR、语义检索、文档解析扩展及所用模型。
- OCR 原生运行库；检查实际制品适用的许可证和例外条款，不能只依据上层 Python 包的许可证判断。
- 图标、熊猫、第三方站点标识和示例文章素材。

项目采用什么许可证，需要维护者决定。本次未替项目选择许可证，也没有认定任何依赖要求整个项目采用特定许可证。

## 建议增加的协作文件与自动检查

目前未发现 `.github` 工作流、CONTRIBUTING、SECURITY 或 CODE_OF_CONDUCT。建议先补最小集合：

1. CONTRIBUTING：开发环境、目录结构、测试命令、提 PR 规则和代码风格。
2. SECURITY：支持版本、漏洞报告方式及不要在公开 Issue 中粘贴资料或密钥的说明。
3. Issue / PR 模板：系统版本、芯片、App 版本、复现步骤和脱敏日志。
4. CI：后台无真实模型调用的测试、浏览器插件检查、macOS 编译检查、凭证扫描与依赖检查。保留现有 Makefile 入口，补齐 macOS 检查与环境安装说明，不需要更换开发框架。
5. 简短项目路线与维护范围：明确目前主要交付 macOS Apple Silicon，移动端、云端和历史服务处于什么状态。

行为准则、完整英文文档、自动发布、公证和网站可以逐步补充，不需要为首次公开先搭建一套复杂平台。

## 推荐执行顺序

1. 确定开源许可证、版权主体和素材授权范围。
2. 确定公开目录清单，筛选验收材料并补强忽略规则。
3. 补第三方声明，整理当前 README、隐私说明与构建说明。
4. 在独立干净检出中验证源码完整性、基础测试和轻量 App 构建。
5. 对最终暂存内容和要推送的历史重新扫描，审核公开快照。
6. 发布源码及首个版本；DMG、校验文件和发布说明放到 Releases。
