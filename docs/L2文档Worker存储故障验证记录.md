# L2 文档 Worker 存储故障验证记录

日期：2026-10-01。范围：文档解析结果事务及任务开始状态事务的受控存储故障。

## 本轮内容

在 `services/api/tests/test_storage_failures.py` 新增两项测试，并为测试 Worker 显式指定同一临时资产目录。使用独立 SQLite 文件、合成 CSV 和测试解析器，不执行真实用户文档、云端调用、OCR 或设备满盘操作。生产 API、Worker 和客户端没有修改。

## 实测

### 解析结果遇到 SQLite 容量限制

1. 保存合成 CSV，先通过现有补充接口保存用户补充，记录当前版本 ID。
2. 压缩独立测试数据库并限制 SQLite 页数，测试解析器返回足够大的合成正文，SQLite 实际产生 `database or disk is full`。
3. `run_document_once` 回滚新版本和证据，任务变为 `failed`、错误类别为 `OperationalError`，已有资料仍为 `usable`，原版本 ID 和用户补充不变。八类业务表计数不增加，下载原件的字节与输入一致。
4. 解除容量限制后，**通过测试脚本管理性操作**将任务改为 `pending`，再调用文档 Worker。任务完成，尝试次数为 2，只新增一个版本，正文包含新的解析结果及原有用户补充。

步骤 4 用于证明存储恢复后的底层处理能力，不是现有客户端的恢复流程。

### 任务开始状态提交失败

1. 保存合成 CSV，在临时数据库安装触发器，拒绝 `document_jobs` 更新。
2. Worker 将任务改为 `running` 的初始提交抛出 `IntegrityError`；会话关闭后事务回滚，任务仍为 `pending`、尝试次数为 0、资料仍为 `pending`，原件字节和业务表计数不变。
3. 移除触发器，使用新会话再次调用 Worker，任务完成，尝试次数为 1，仅新增一个版本。

本测试调用实际任务函数，使用新会话模拟下一次 Worker 尝试。没有在这一故障中启动实际宿主或验证客户端自动恢复；此前进程恢复测试是另一份证据，不能混作本轮整条链路通过。

## 验证结果

- 存储故障测试文件共 **5 项通过**，其中本轮新增 2 项。
- 完整 API 和运行包工具回归 **119 项通过**，已有 Starlette/AnyIO 弃用提示 1 项。
- `git diff --check` 通过。
- 汇总见 [worker-storage-failures.json](./verification/l2/worker-storage-failures.json)。没有改变数据库结构、文件格式或迁移步骤，本轮无需重建随包客户端。

## 恢复入口缺口与待确认事项

现有文档任务查询只处理 `pending`；启动时只把 `running` 恢复为 `pending`，不会重排 `failed`。目前 API 和客户端提供 PDF OCR 重试，但没有对应的普通文档解析重试入口。对上述已进入 `failed` 的文档，用户释放空间后无法直接重新排队。

已按用户 AGENTS.md 第 17 条请求明确确认：为已有原件增加手动文档解析重试入口，保留已有版本和用户补充，防止重复排队。确认前不修改生产实现。此前后台空间不足提示的修复也仍待确认，本轮未把自动心跳视为这些新增修复的明确授权。

## 尚未验证

失败状态本身也无法写入的情况、语义索引/PDF OCR/网页任务的空间不足、实际满盘、宿主和客户端完整故障恢复链路。上述两个受控场景不能证明所有 Worker 满盘路径可靠；L2 仍保留其余验收门槛。
