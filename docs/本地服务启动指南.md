# 本地服务启动指南

本页介绍**外置后台开发模式**。完整本地客户端日常构建请先阅读 [macOS BUILD](../apps/macos/BUILD.md)：App自动启动内置API/Worker，AI网关独立运行。下面的裸`build.sh`会构建开发后台模式客户端并移除已有内置运行包，不能作为完整客户端交付命令。

以下命令都从**项目根目录**执行。开发外置服务可使用“方案 A”；验证容器部署时使用“方案 B”。两套方案及App本地库的数据互不相通，切换后看到不同资料是正常现象。**不要同时启动监听8000端口的两组API，也不要让两个Worker处理同一个数据库。** 模块职责和更新规则见 [API BUILD](../services/api/BUILD.md)、[Worker说明](../services/worker/README.md)和 [AI网关 BUILD](../services/ai_gateway/BUILD.md)。

| 组件 | 方案 A：本机进程 | 方案 B：Docker Compose | 何时需要 |
| --- | --- | --- | --- |
| 数据库 | SQLite 文件 `services/api/pka-dev.db`，API 首次启动自动建表，无需单独启动 | `database`：PostgreSQL 17，容器内 `database:5432` | 必需，二选一 |
| API 后台 | Uvicorn，`127.0.0.1:8000` | `api`，映射到本机 `8000` | 必需；登录、资料、搜索和健康检查 |
| Worker | 独立 Python 进程 | `worker` 容器 | 文件解析、PDF/OCR、网页读取、语义索引和删除清理；建议与 API 同时运行 |
| Crawl4AI | 默认不启用 | 可选 `crawl4ai` 容器 | 仅在设置中选用浏览器方式读取网页时需要 |
| Mac 客户端 | 构建后的 `.app` | 仍在 Mac 上运行，连接本机映射的 8000 端口 | 使用桌面界面时需要 |
| 浏览器插件 / 移动端 / MCP | 各自按需启动或加载 | 同左 | 非后台常驻服务 |

## 方案 A：本机 API + Worker + SQLite（推荐日常使用）

首次准备，仅需执行一次；已有 `.venv` 且依赖已安装时跳过：

```bash
python3 -m venv .venv
.venv/bin/pip install -r services/api/requirements.txt
.venv/bin/pip install -r services/api/requirements-ocr.txt
```

打开两个终端，都切到项目根目录。**终端 1：API**：

```bash
PYTHONPATH=services/api .venv/bin/uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

**终端 2：Worker**：

```bash
PYTHONPATH=services/api:. .venv/bin/python -m services.worker.main
```

Worker 空闲时会持续等待任务，不持续打印日志是正常的。`--reload` 只会自动重启 API；修改 Worker 代码后，应在终端 2 按 `Ctrl+C`，再执行上面的 Worker 命令。首次 OCR 或语义检索可能需要下载本地模型。语义索引失败后需要重试时，用以下命令代替普通 Worker 命令：

```bash
PYTHONPATH=services/api:. .venv/bin/python -m services.worker.main --retry-semantic
```

若本机网络代理把公开域名映射到 `198.18.0.0/15`，网页读取遇到地址校验失败时，可**仅在本机开发环境**改用下面的 Worker 命令；普通网络不要加该变量：

```bash
PKA_WEB_ALLOW_FAKE_IP=1 PYTHONPATH=services/api:. .venv/bin/python -m services.worker.main
```

数据库文件是 `services/api/pka-dev.db`，上传原件在 `services/api/uploads/`，语义模型默认在 `services/api/model-cache/`。这些路径由 API 配置确定；Worker 与 API 必须使用同一套 `PKA_DATABASE_URL`、`PKA_UPLOAD_DIR` 和语义模型配置。默认命令已满足这一点。SQLite 不需要 Docker，也不需要运行 PostgreSQL。

**终端 3：Mac 客户端**。首次构建或修改 Swift 代码后重新构建；平时只需 `open`：

```bash
bash apps/macos/scripts/build.sh
open apps/macos/dist/知识收集箱.app
```

当前客户端默认连接 `http://127.0.0.1:8000`。本机开发登录首次配置后会自动恢复会话；如果 API 没启动，客户端仍无法连接。开发登录接口只在 `PKA_ENVIRONMENT=development` 或 `test` 时开放；以上两套开发命令默认是 `development`。客户端不是服务器，不需要保持启动终端。

## 方案 B：Docker Compose（PostgreSQL + API + Worker）

先启动 Docker Desktop。从项目根目录执行：

```bash
docker compose -f infra/compose.yaml up -d --build
```

这条命令启动 `database`、`api`、`worker`。Compose 内的 PostgreSQL **没有映射到 Mac 的 5432 端口**，只供容器内的 API/Worker 使用；数据库数据、上传原件、OCR 模型和语义模型分别保存在 `pka-postgres`、`pka-uploads`、`pka-ocr-models`、`pka-embedding-models` 卷中。API 仍可从 Mac 的 `http://127.0.0.1:8000` 访问；Mac 客户端构建和打开命令与方案 A 相同。不要在此方案中另开本机 API 或本机 Worker。

查看状态与日志：

```bash
docker compose -f infra/compose.yaml ps
docker compose -f infra/compose.yaml logs -f api worker
docker compose -f infra/compose.yaml exec database pg_isready -U pka
```

仅需在容器网络内启动数据库时可执行 `docker compose -f infra/compose.yaml up -d database`；**这不会让本机 Python 进程直接连上 PostgreSQL**，因为当前 Compose 未发布数据库端口。日常本机开发请用方案 A 的 SQLite；容器化请启动整套方案 B。

更新 API/Worker 代码或依赖后重新构建并启动：

```bash
docker compose -f infra/compose.yaml up -d --build
```

停止整套容器：

```bash
docker compose -f infra/compose.yaml down
```

`down` 默认保留上述数据卷。**不要随意加 `-v`**，它会删除 Compose 管理的数据库、上传文件和模型卷。仓库中的 Compose 数据库用户名与密码仅为本地开发示例，正式环境须改为独立密钥配置。

### 可选：Crawl4AI 网页浏览器服务

仅当客户端“网页读取方式”选择 Crawl4AI 时使用。首次启用时，把一个随机令牌写入**未纳入版本控制**的 `infra/.env`，后续启动沿用同一个值：

```bash
test -f infra/.env || cp infra/.env.example infra/.env
rg -q '^PKA_CRAWL4AI_TOKEN=.+$' infra/.env || printf '\nPKA_CRAWL4AI_TOKEN=%s\n' "$(openssl rand -hex 32)" >> infra/.env
docker compose --env-file infra/.env -f infra/compose.yaml -f infra/compose.crawl4ai.yaml up -d --build
```

上面的合并配置会启动数据库、API、Worker 和 Crawl4AI，Worker 自动使用容器内 `http://crawl4ai:11235`。不要每次启动都重新生成令牌。查看日志或停止时也带上两份 Compose 文件和同一份环境文件：

```bash
docker compose --env-file infra/.env -f infra/compose.yaml -f infra/compose.crawl4ai.yaml logs -f worker crawl4ai
docker compose --env-file infra/.env -f infra/compose.yaml -f infra/compose.crawl4ai.yaml down
```

普通网页读取只需 API 和 Worker，**不需要** Crawl4AI。当前 Compose 的 Crawl4AI 没有发布到 Mac 主机端口，不可直接给方案 A 的本机 Worker 使用。

## 按需使用的客户端和 Agent 接入

浏览器插件不是常驻服务。修改插件代码后构建，在 Chrome/Edge 扩展管理页“加载已解压的扩展程序”，选择 `apps/extension/dist/`；在插件设置中填 API 地址，并从 Mac 客户端“设置”复制完整开发 Access Token：

```bash
cd apps/extension
npm run build
```

移动端为 Expo 开发服务，可按需启动，配置方式见 [移动端说明](../apps/mobile/README.md)：

```bash
cd apps/mobile
test -f .env.local || cp .env.example .env.local
npm install
npm start
```

MCP 为 Agent 客户端按需拉起的 **stdio 进程**，不需要在普通 Mac 客户端使用时单独启动。配置 Agent 连接并获得 Agent Token 后，可手动运行：

```bash
export PKA_AGENT_TOKEN="<从创建 Agent 连接的响应获取>"
PYTHONPATH=services/api .venv/bin/python -m app.mcp_server
```

若运行方案 B，MCP 也必须使用 Docker 内的 PostgreSQL；可在有 `PKA_AGENT_TOKEN` 环境变量的终端运行下面的命令，以 stdio 方式连接 Agent 客户端：

```bash
docker compose -f infra/compose.yaml exec -T -e PKA_AGENT_TOKEN="$PKA_AGENT_TOKEN" api python -m app.mcp_server
```

这里的 **Agent Token** 与 Mac 客户端/浏览器插件使用的 **App Access Token** 不是同一种令牌。真实令牌不要写进仓库或示例配置。

## 检查与排障

API 启动后可在任意终端检查：

```bash
curl -fsS http://127.0.0.1:8000/health
```

预期返回 `{"status":"ok","milestone":"M1"}`。若连接被拒绝，先确认 API 终端是否仍在运行，或用 `docker compose -f infra/compose.yaml ps` 查看容器状态。若 API 正常但上传文件一直显示“识别中”，确认 Worker 与 API **使用同一数据库和上传目录**，并查看 Worker 终端或 `docker compose -f infra/compose.yaml logs -f worker`。若切换运行方案后“资料不见了”，先检查当前连接的是 SQLite 还是 Docker PostgreSQL；不要通过删除数据库来处理。

本机方案在两个服务终端分别按 `Ctrl+C` 停止；Docker 方案使用 `docker compose ... down`。更详细的认证、OCR 和检索配置见 [API 文档](../services/api/README.md)，Mac 客户端功能见 [Mac 文档](../apps/macos/README.md)。
